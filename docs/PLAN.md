# План разработки

## Принципы

- Игра всегда восстановима: операция либо завершается целиком, либо откатывается.
- Сначала ядро и тесты, потом окно. До этапа 8 всё работает из командной строки.
- Ядро (`core`) не знает об играх. Всё специфичное для игры живёт в её пакете.
- Каждый этап заканчивается проверкой на реальной игре.

### 1. Файловая основа (`core/fsx`)

Атомарная запись (временный файл → переименование), хеширование, жёсткие ссылки
с проверкой «тот же диск», перенос в Корзину, безопасное склеивание путей.

Готово, когда тесты покрывают обрыв записи, длинные пути, кириллицу в путях
и файл, занятый другим процессом.

Принято: хеш — SHA-256; вызовы Windows API — через `golang.org/x/sys`;
если Корзина недоступна, файл остаётся на месте и возвращается ошибка.

### 2. Хранилище и манифест (`core/store`, `core/manifest`, `core/profile`)

- Хранилище: исходный архив, распакованная версия, хеши файлов, метаданные.
- Несколько версий одного мода рядом.
- Манифест: для каждого файла в игре — чей он, какой хеш, когда развёрнут.
- Профили как списки «мод, включён, позиция».

Готово, когда мод можно добавить, получить список его файлов и удалить
без остатков, а база переживает обрыв записи.

Принято: архивы zip, 7z и rar (`core/archive`, формат по содержимому);
исходный архив хранится рядом с распакованными файлами; удаление — в
Корзину, насовсем только после отдельного подтверждения. База — JSON-файлы,
каждый пишется атомарно. Окно уже работает с хранилищем: «Добавить мод»,
«Показать файлы», «Удалить мод», переключатели. Пока игра не ищется (этап 4),
хранилище лежит в `%LOCALAPPDATA%\Modvault`, другое место задаёт
переменная `MODVAULT_HOME`.

### 3. Развёртывание и журнал (`core/deploy`, `core/journal`)

- Расчёт разницы между тем, что есть в игре, и тем, что должно быть по профилю.
- Применение ссылками, откат на копирование при разных дисках.
- Журнал: план записывается до начала, шаги отмечаются, при сбое — откат.
- Восстановление при запуске, если прошлый сеанс оборвался.
- Проверка целостности: чужие правки, пропавшие и лишние файлы.
- Конфликты файлов между модами с явным правилом, кто побеждает.

Готово, когда тест «убить процесс на каждом шаге» всегда приводит либо
к старому, либо к новому состоянию.

Принято: в конфликте побеждает мод ниже в порядке, победителя можно
закрепить в профиле (выбор в окне — этап 8); чужой файл на месте мода
сохраняется и возвращается при снятии; после сбоя развёртывание откатывается.
Файл мода, изменённый вне программы, не удаляется, а переносится в папку
`displaced` состояния. Пока нет плагина игры, файлы ложатся по путям из
архива, а папку игры выбирают в окне вручную.

### 4. Плагин Darktide (`game/darktide`)

- Поиск игры: Steam, Xbox, ручной выбор.
- Разбор архива: обычный мод, вложенная `mods/`, `binaries/`, оверлей в корень,
  папки-обёртки, кривые имена.
- Чтение и запись `mod_load_order.txt`.
- Патч `bundle_database.data`: бэкап привязан к хешу оригинала, устаревший
  бэкап не накатывается никогда.
- Определение чужих патчеров и сосуществование с ними.
- Установка DML и DMF.

Готово, когда на чистой игре ставятся DML, DMF и десяток модов, игра
запускается, а после «выключить всё» файлы игры побайтно совпадают с исходными.

Принято: базу бандлов патчит `tools/dtkit-patch.exe` из DML — на копии во
временной папке, а в игру результат кладёт развёртывание, с резервной копией
оригинала. Наш патч совпадает с патчем dtkit в игре байт в байт. Если Steam
обновил файл, подменённый модом, прежняя резервная копия признаётся
устаревшей и не возвращается никогда. Нераспознанный архив не добавляется.
В папку игры со следами Vortex или Servo-Modquisitor Modvault не
развёртывает до этапа 5. Проверка на настоящей игре перенесена на этап 5:
игра автора управляется Vortex.

### 5. Командная строка и «усыновление» (`cmd/modvault`)

- Команды: установить, удалить, включить/выключить, развернуть, проверить,
  откатить, профили, состояние.
- «Усыновление»: существующая папка `mods/` переносится в хранилище
  без переустановки.
- Режим «показать, что будет сделано» без изменений.

Готово, когда существующую установку можно принять под управление и вернуть
обратно без потерь.

Принято: логика окна вынесена в пакет `manager`, окно и командная строка —
оболочки над ним. Хранилище по умолчанию — папка `Modvault` в корне диска
с игрой (место запоминается в `%LOCALAPPDATA%\Modvault\location.json`).
«Перенять у Vortex» принимает моды из его хранилища копиями, профиль — по его
порядку загрузки, победителей конфликтов — как у него, сохранённые
оригиналы (`*.vortex_backup`, `bundle_database.data.bak`) — как резервные
копии. Файлы игры при этом не меняются; Vortex отсоединяется: его
`vortex.deployment.json` уходит к Modvault. «Вернуть Vortex» кладёт всё
обратно ссылками на его хранилище, побайтно как было, и забывает учёт
Modvault; моды остаются в хранилище. Servo-Modquisitor после подтверждения
не учитывается. Пробный прогон на игре автора: 141 мод, 139 развёрнуто,
1469 файлов, расхождений нет. Само усыновление на игре автор делает в окне.

### 6. Правила и автосортировка (`rules`)

- Формат правил: обязательный порядок, «раньше/позже», зависимости,
  несовместимости, устаревшие.
- Сортировка с обнаружением циклов: цикл показывается, моды не теряются.
- Проверки с предложением исправления.
- Чтение внешних файлов правил как дополнительного источника.

Готово, когда на наборе из 100+ модов сортировка стабильна и ни один мод
не пропадает.

Принято: Servo-Modquisitor не используется вовсе — ни как источник правил,
ни как «другой менеджер»; Modvault работает только с Vortex. Правила берутся
из файлов `.mod` (`load_before`, `load_after`, `require`) и из встроенных
правил загрузчика. Списков несовместимых и устаревших модов нет: они были
только у SMQ. Сортировка — по кнопке, с просмотром; проверки только
предупреждают.

Загрузчик автора — AML («Auto Mod Loading and Ordering»): он не читает
`mod_load_order.txt`, сам грузит все папки из `mods/` и упорядочивает их,
а мод без нужного `require` молча пропускает. Для него сортировка ставит
список в порядок из журнала загрузчика `mods/auto_mod_loader_log.txt` — так
игра загрузила моды в последний раз; на игру это не влияет. Для обычного DML
та же сортировка попадает в `mod_load_order.txt`. Разбор правил проверен на
наборе автора: 140 модов, 40 правил, порядок из журнала соблюдает их все.

### 7. Nexus (`nexus`)

- Вход по личному API-ключу, ключ в хранилище учётных данных Windows.
- Приём ссылок `nxm://`, передача уже запущенной копии программы.
- Загрузка во временный файл, докачка, сверка хеша, затем — в хранилище.
- Проверка обновлений по ID файла, пакетно, с учётом лимитов.
- Обновление: новая версия ставится рядом, старая удаляется после успеха.

Готово, когда кнопка «Mod Manager Download» приводит к установленному моду,
а обрыв сети посреди загрузки ничего не портит.

Принято: в сеть программа ходит только по просьбе — обновления проверяются
по кнопке. Первая проверка спрашивает о каждом моде, следующие — одним
запросом «что менялось» и только об изменившихся; итог лежит в
`nexus/updates.json` хранилища. У модов, принятых от Vortex, номера файла нет,
поэтому их версия сравнивается с последним основным файлом страницы; у
скачанных через Modvault — по истории замен файла.

Ссылки `nxm://` Modvault берёт на себя щелчком по «Ссылки nxm» в строке
состояния и тем же щелчком возвращает прежней программе; «Вернуть Vortex»
возвращает и их. Окно одно: вторая копия, запущенная ссылкой, отдаёт её
первой. Без Premium Nexus отдаёт файл только по ссылке с сайта, поэтому
«Обновить» открывает страницу файлов мода; с Premium качает сразу.

Файл качается в `downloads/*.part` с докачкой, сверяется по размеру и по MD5
(Nexus узнаёт свои архивы; свежий файл он может ещё не знать) и только потом
попадает в хранилище. Название и версия берутся из ответа Nexus. Основной
файл обновляет мод с тем же номером на Nexus, дополнение (optional) встаёт
отдельным модом. После обновления в хранилище остаются новая версия и одна
прежняя; версии, выбранные в других профилях, не удаляются; остальные уходят
в Корзину. То же при добавлении архива с диска.

Команды: `modvault nexus login | logout | check | get <ссылка>`. Раздел
«Загрузки» в окне — на этапе 8; пока ход загрузки виден всплывающей строкой.
Формат ответов Nexus проверен только на поддельном сервере: с настоящим
ключом проверяет автор.

Доработки по ходу проверки автором:

- Проверка обновлений показывает ход: полоса над списком и столбец
  «Обновление» с отметкой у каждого мода (в очереди, проверяется, актуален,
  есть версия). У версии новее стоит значок «обновить».
- Без Premium «обновить» открывает страницу загрузки нужного файла
  (`?tab=files&file_id=…&nmm=1`, как у Vortex), а не список файлов.
- Обновление не спрашивает, развёртывать ли: включённый мод сразу получает
  новую версию в игре, выключенный остаётся выключенным. Если в профиле
  ждут другие изменения, без спроса они не развёртываются.
- «Играть» запускает `binaries/Darktide.exe` напрямую, без окна лаунчера, с
  теми же параметрами, что и лаунчер; Steam должен быть запущен.

### Наборы модов

Набор — это профиль: какие моды включены. В окне: меню «Набор» в шапке
(выбрать, создать копию, переименовать, удалить) и выделение нескольких
модов щелчком с Ctrl или Shift с действиями «В новый набор», «Добавить в
набор», «Включить», «Выключить».

Принято: в каждом наборе сами включаются загрузчик, фреймворк и моды,
которых требуют выбранные; переключение набора сразу приводит к нему игру;
версия мода одна на все наборы — обновление действует в каждом. Команды:
`modvault profile new <имя> [мод...]`, `modvault profile switch <имя>`.

### 8. Окно программы

- Технология — Wails 2: страница на HTML и CSS внутри WebView2, логика на Go,
  без Node и сборщиков; шрифты вшиты в программу.
- Оболочка окна сделана досрочно, сразу после этапа 1, чтобы результат был
  виден по ходу работы: `cmd/modvault-gui`, пакет `ui`. Пока ядро не
  подключено, она показывает демонстрационные данные с пометкой, а кнопки без
  ядра сообщают, на каком этапе заработают. Сборка:
  `go build -tags desktop,production -ldflags "-H windowsgui" ./cmd/modvault-gui`.
  Значок и манифест: `go run github.com/tc-hib/go-winres@latest make --arch amd64`
  в папке `cmd/modvault-gui`.
- Стиль — гримдарк: тёплые тёмные поверхности, латунные рамки, цвет пергамента,
  потёртая оранжевая шапка со знаком ZD.
- Главное окно: строка состояния под шапкой, блок «Требуют внимания», список
  модов профиля на всю ширину, карточка выбранного мода справа, план
  развёртывания внизу.
- Список модов, перетаскивание архивов, профили, порядок, проверки, журнал
  действий, настройки, мастер первого запуска.
- Русский и английский интерфейс.

Готово, когда всё, что умеет командная строка, доступно из окна, и ни одна
ошибка не остаётся только в логе.

### 9. Русификатор

Слой переводов поверх модов: подключается и снимается как обычный мод,
не трогая файлы оригинала.

### 10. Выпуск

Сборка релиза, сведения о версии в exe, контрольные суммы, самообновление,
инструкция.

## Риски

| Риск | Что делаем |
|---|---|
| Жёсткие ссылки не работают (другой диск, exFAT) | Определяем заранее, переходим на копирование с тем же манифестом |
| Обновление игры меняет формат бандла | Патч не применяется, если не найден ожидаемый якорь |
| Проверка файлов в Steam затирает развёрнутое | Проверка целостности это видит и предлагает развернуть заново |
| Лимиты Nexus API | Кэш ответов, пакетные запросы |
